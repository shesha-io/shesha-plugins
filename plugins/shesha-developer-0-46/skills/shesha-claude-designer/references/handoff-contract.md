# Handoff contract — roles, inputs/outputs, sequencing

The conductor (`shesha-claude-designer`) coordinates six specialists. This is the contract between them.

**Preference order for building screens (STRICT):** `create-crud-form` (canonical CRUD) → `shesha-form-edit` (non-canonical Shesha form using existing components) → `create-custom-component` + `shesha-form-edit` (fill a missing component to KEEP the screen on the form-configuration road) → LAST RESORT: `create-custom-page` (pure React). Form-configurations retain the framework's data-loader / permissions / validation / versioning / import-export; a custom page reimplements every one of those responsibilities. Reach past the form-config routes only when a concrete capability cannot be expressed even with a new custom component — and name it when you do.

**Every handoff carries file paths, never file contents.** All of them are relative to `$RUN_DIR`, the single run directory created in [SKILL.md](../SKILL.md) Step 0 (`.claude/shesha/runs/<run-slug>/`) — older text saying `<workdir>` means this. Each dispatch prompt must state `$RUN_DIR` explicitly; an agent left to invent a scratch location writes somewhere nobody reads. Returning a large JSON blob through the conductor's context instead of a path is the single easiest context saving in the pipeline, and it also means the artifact still exists after a compaction.

## Roles

| Skill | Owns | Must NOT |
|---|---|---|
| `shesha-claude-designer` | ingest design, comprehend→plan, sequence, gate, verify end-to-end | author form JSON, pick hexes, push |
| `shesha-design-comprehension` | per-screen measured layout blueprint + placement verification (the probe + the diff) | author form JSON, pick hexes, push |
| **`create-crud-form`** *(preference 1 — CRUD)* | **canonical CRUD structure — the FIRST POINT OF REFERENCE for the five archetypes (`list-card` table, `list-card` datalist-of-cards, `capture` in-modal create, `record-detail`, `inline-card` row-template mini-card).** Copies one of six sample seeds byte-exact, swaps entity bits, runs the 16-rule pre-push validator, pushes (a saved form is live on 0.46). **The seed's baked-in aesthetic IS the intended output — every screenshot in `create-crud-form/assets/screenshots/` shows exactly what ships.** | receive a `shesha-design-system` styling pass; be re-styled to match a custom brand; be re-judged by `design-critic`; build non-canonical shapes or React-only pages |
| `shesha-form-edit` *(preference 2 — non-canonical Shesha form)* | **NON-CANONICAL Shesha-form structure using existing form-designer components** — hubs, wizards, form-designer-expressible dashboards, solution-maps, master-detail splits with junction subtables, inline-editable tables; CRUD wiring, validation, push (saved = live on 0.46); **splits via flex `container` rows (never `columns`), sized via `desktop.dimensions.width`**. Also owns single-form edits (add a field, wire a button) on any existing form. Consumes custom components produced by `create-custom-component` when used | apply v7 appearance blocks itself; author `columns`; pick tokens/hexes; build canonical CRUD when `create-crud-form` would cover it; scaffold plain React pages when `create-custom-component` + this skill would cover the gap |
| **`create-custom-component`** *(preference 3 — extend the toolbox to keep the screen on the form-config road)* | **new designer components for package projects** (enterprise / reporting / workflow). Builds `packages/<pkg>/src/designer-components/<name>/{model.ts, settings.ts, index.tsx}` + optional `components/<name>/index.tsx`, registers in the package's `formDesignerComponents` toolbox group. Supports input / output / container semantics; uses `SettingsFormMarkupFactory` + `fbf()` for the component's configuration panel. **Its output is then embedded inside a form-config via `shesha-form-edit`** — the form retains every framework guarantee | build screens itself; scaffold routes; author form JSON directly; own the app's `src/screens/` or `src/app/` — those belong to `create-custom-page` when needed |
| `create-custom-page` *(preference 4 — LAST RESORT)* | **bespoke React + Ant Design screens ONLY when the form-designer, even with a new custom component, cannot express the screen** — interactive drag-and-drop UIs, integration consoles, marketing / landing pages, bespoke data browsers with panel-splits / keyboard-shortcuts / multi-selection semantics outside typical form-designer expectations. Scaffolds `src/screens/<name>/index.tsx`, registers it in `src/screens/index.tsx`, creates the Next.js route entry under `src/app/(main)/dynamic/<route>/page.tsx` (or `src/app/no-auth/` when public). Fetches via `fetch` + `useSheshaApplication` (`backendUrl` / `httpHeaders`). **This route bypasses the framework's data-loader / permissions / validation / versioning / import-export guarantees — the application code has to reimplement them.** Always name the specific missing capability that forced this route | build Shesha form-designer JSON markup; author Shesha components; be preferred over `create-custom-component` + `shesha-form-edit` when a custom component would have closed the gap; build shapes covered by `create-crud-form` |
| `shesha-design-system` | **all appearance** — app theme (`Shesha.ThemeSettings`: primary/semantic colours, canvas, sidebar, `components.<type>` defaults; reaches ALL screens including custom pages, but **not** radius/heights/font) + per-component v7+ style blocks (Shesha form-designer components only) + the v7 mechanics/channels docs + the capability matrix + the restoring-pre-0.46-look guide (migration-injected defaults); audit. **Per-component v7 pass NOT invoked on `create-crud-form` outputs** (seed aesthetic is deliberate) **NOR on `create-custom-page` outputs** (uses AntD-native components — the app theme carries the brand through). | author structure, wire CRUD, push, or author `columns`; touch a `create-crud-form` output |

## Contracts

**Designer → comprehension (Step 2, per screen)**
- Parent provides: `$RUN_DIR`, design source(s) + detected fidelity tier + screen name + (Tier A) repo/source paths + pinned viewport.
- Comprehension returns: **paths only** — `$RUN_DIR/blueprints/<screen>.blueprint.md` (archetype + `layout-tree` + `bindings` + `assertions`) and the saved probe `$RUN_DIR/probes/<screen>.design.layout.json`.

**Designer → create-crud-form (Step 4a, per screen — CANONICAL CRUD) — "Contract A1"**
- Use for archetypes: `list-card` (table OR datalist-of-cards), `capture` (in-modal create), `record-detail`, `inline-card` (row-template mini-card).
- Parent provides: `$RUN_DIR`, the screen's **`blueprint.md` path** (evidence of archetype + bindings), the entity modelType (or "resolve from module"), the form identity (module + name), and the standard headless context block (Backend URL / Username / Password / Module / Working directory = the target project root that hosts a `.sln`, not `$RUN_DIR`). For the `list-card` datalist-of-cards variant, name BOTH forms — host + row-template subform.
- create-crud-form returns: form(s) created (module + name + id — always the host, plus the row-template subform on the datalist variant), the resolved `{name, module, fullClassName}`, pushed/saved state, the staged markup path(s) under `$RUN_DIR/staged/`, a validator-clean confirmation (all 16 R-rules pass, exit 0), and any disclosures (assumed reflist modules, missing target forms) as compact data.
- **The conductor verifies the disk before accepting any of it:** same verify-artifact call as Contract A2 (below — the shared form-JSON verify path). A validator-clean claim is a claim; the file on disk is the evidence.
- **No follow-up styling contract.** After Contract A1 completes and the artifact verifies, the conductor jumps directly to gate 5a → 5a.5 and finishes. **Do NOT invoke `shesha-design-system` (Step 4b), gate 5b (visual audit), or gate 5c (`design-critic`) on the returned form.** The seed's canonical Shesha aesthetic (grey pageShell / white cards with the canonical soft shadow / blue accents / pill `refListStatus` cells / avatar circles) is the intended output; every screenshot in `create-crud-form/assets/screenshots/` shows exactly what the built form will look like. A styling pass, a visual audit against a custom theme, or a critic verdict of "generic" would all fight the seeds — and would erase what makes this route the highest-fidelity, lowest-turn-cost path for CRUD.

**Designer → shesha-form-edit (Step 4a, per screen — NON-CANONICAL SHESHA FORM, or single-form edits) — "Contract A2"**
- Use when the archetype is `hub`, `wizard`, `solution-map`, a form-designer-expressible dashboard, a master-detail split with junction subtables, an inline-editable table — anything without a byte-exact sample seed that IS expressible in the Shesha form-designer. Also use for field-level edits on any existing form regardless of archetype (`create-crud-form` is a full-form builder, not an edit tool).
- Parent provides: `$RUN_DIR`, the screen's **`blueprint.md` path**, the entity modelType (or "resolve from module"), the form identity (module + name), and the target backend context (if headless).
- shesha-form-edit returns: form created/edited (module + name + id), the detected version-profile facts, the resolved modelType, pushed/saved state, the staged markup path under `$RUN_DIR/staged/`, **and a structural-integrity confirmation** — plus enough to run the placement probe (it builds the form `shesha-design-comprehension` will re-measure).
- **The conductor verifies the disk before accepting any of it:** `node <FORM_EDIT_SKILL_ROOT>/scripts/verify-artifact.mjs <staged-path> --backend <url> --token $RUN_DIR/access-token --json`. Exit `0` pass · `1` fail · `2` unreadable · `3` partial. Agents in this pipeline have twice reported a completed form that was absent or referenced forms that did not exist; a returned verdict is a claim, the file is the evidence.

**Designer → create-custom-component (Step 4a, per screen — WIDEN THE FORM-DESIGNER TOOLBOX before falling to a custom page) — "Contract A3"**
- Use when a screen is form-shaped but the Shesha form-designer is missing ONE component the blueprint calls for (a specific chart type, a rating input, an image annotator, a Kanban card, a signature pad, etc.). This contract is a PRECURSOR to Contract A2 — after the new component is registered in the toolbox, dispatch Contract A2 (`shesha-form-edit`) to build the form-config that uses it. Do NOT fall to Contract A4 (`create-custom-page`) unless building the component is genuinely more effort than the payoff.
- Parent provides: `$RUN_DIR`, the **package** the component should live in (enterprise / reporting / workflow), the **component name** (camelCase), **display name**, **description / purpose**, **category / toolbox-group name**, whether it is an **input** / **output** / **container**, the **custom property list** (from the blueprint's `bindings` block for the missing capability), the **icon name** (from `@ant-design/icons`), and whether it needs a separate reusable UI component under `packages/<pkg>/src/components/<name>/`.
- create-custom-component returns: **paths only** — the created `packages/<pkg>/src/designer-components/<name>/{model.ts, settings.ts, index.tsx}`, the updated `packages/<pkg>/src/designer-components/index.ts` (registry entry appended in the right toolbox group), optionally `packages/<pkg>/src/components/<name>/index.tsx`, and the registered **component type name** (used in form-designer JSON as `type: "<componentName>"`).
- **The conductor verifies these artifacts on disk before accepting any of it:** each returned path must exist and be non-empty; the registry file must include the new component in its `formDesignerComponents` group; the component type name must be unique in the toolbox. If verification fails, route back to `create-custom-component` with the missing artifact named. Then re-dispatch Contract A2 (`shesha-form-edit`) with the new component type name in the requirements.

**Designer → create-custom-page (Step 4a, per screen — LAST RESORT, CUSTOM REACT PAGE) — "Contract A4"**
- Use ONLY when Contracts A1 / A2 / A3 / A4 have all been ruled out — the screen cannot be expressed as a Shesha form-config even with a new custom component. Interactive drag-and-drop UIs, integration consoles, marketing/landing pages, bespoke data browsers with panel-splits / keyboard-shortcuts / multi-selection semantics outside typical form-designer expectations. The blueprint header declares `Archetype: <shape> — custom-page variant · reason: <specific-capability>` and its `layout-tree` describes React component composition (Card / Row / Col / Space / Table / Chart placements) rather than form-designer nesting.
- **Before dispatching this contract, log the reason in `run-log.md`:** which capability the form-designer (even with a plausibly-new custom component) could not have expressed. This is the audit trail for why the run left the paved road.
- Parent provides: `$RUN_DIR`, the screen's **`blueprint.md` path**, the **frontend project root** (Working directory — where `src/screens/` and `src/app/(main)/dynamic/` live), the screen name (kebab-case), the route path (slash-separated), the display title, whether the screen is public or authenticated, and a description of what the screen must render + fetch. Backend URL + admin credentials only when the screen fetches data — the auth headers are supplied by `useSheshaApplication()` at runtime.
- create-custom-page returns: **paths only** — the created `src/screens/<name>/index.tsx`, the updated `src/screens/index.tsx` (registry entry appended), the created route entry `src/app/(main)/dynamic/<route>/page.tsx` (or `src/app/no-auth/<route>/page.tsx` for public screens), and the runtime URL (`{base_url}/dynamic/<route>`). No backend form id (there's no Shesha form).
- **The conductor verifies these artifacts on disk before accepting any of it:** each returned path must exist and be non-empty; the registry file must include the new screen's entry; the route entry must import from `@/screens/<name>` and render the screen with the display title. If verification fails, route back to `create-custom-page` with the missing artifact named.

**Designer → shesha-design-system (Step 3 theme + Step 4b style)**
- Step 3 (app theme — once per run, reaches ALL screens): parent provides token set / theme name; skill sets `Shesha.ThemeSettings` (primary/semantic colours, canvas, sidebar). This affects Shesha form-designer components AND AntD-native components in `create-custom-page` screens, for colours only; radius/spacing are per-block or per-page.
- Step 4b (per-component v7+ style — `shesha-form-edit` builds only): parent provides `$RUN_DIR`, the token set, the **path** to the built form under `$RUN_DIR/staged/`, version-profile facts (each component's stored version vs its 0.46 current version), recipe list. The styled output stamps current versions and writes explicit values so load-time migrations do not inject defaults.
- shesha-design-system returns: **the path** `$RUN_DIR/staged/<screen>.styled.form.json` (style blocks only, structure untouched), plus app-theme changes, a role→colour trace and audit findings as compact data. It does NOT push, and it does NOT return the styled JSON inline — the parent routes the path through `shesha-form-edit`.
- **NOT invoked for Step 4b on `create-crud-form` or `create-custom-page` builds.** Those routes get only the Step 3 app theme; their per-screen appearance is either baked in (seeds) or inherited from `ConfigProvider` (AntD-native).

**Comprehension ↔ builder (Step 5a.5, per screen)**
- After build+save (0.46 has no publish step), comprehension re-probes the rendered screen into `$RUN_DIR/probes/<screen>.built-r<n>.layout.json` and diffs against the blueprint `assertions`; each mismatch is a routed fix phrased in the **originating builder's** vocabulary:
  - **On a `create-crud-form` build**, the fix is usually a swap-checklist item the agent missed (wrong `dataContext.entityType`, wrong `permanentFilter` shape, tab.id/tab.key collision, `refListStatus.settings` wrapper missing) — return the fix as a specific checklist bullet or a validator rule number (R1–R16) and re-dispatch. If the archetype itself was wrong (e.g. blueprint said `list-card` datalist but the layout diff shows a table structure), the conductor may re-plan — but this is rare, the two `list-card` variants are declared in the blueprint header.
  - **On a `shesha-form-edit` build**, phrase the fix in that skill's vocabulary (move node into the right flex `container` row, give the child its `desktop.dimensions.width`, add `display:"flex"` to a stacking row, wrap rows 2-cell, assign to the right tab).
  - **On a `create-custom-component` + `shesha-form-edit` build**, the fix is usually within the form-config half (see above) — the custom component itself is verified only structurally (registered in the toolbox, correct type name, props match). If the fix is in the component (missing `hidden` guard, wrong `isInput` flag, migration missing), route back to `create-custom-component`. If the fix is in how the component is USED, route back to `shesha-form-edit`.
  - **On a `create-custom-page` build (last resort)**, phrase the fix in React/AntD vocabulary — "the KPI strip should be a single `<Row gutter={16}>` with 6 equal-width `<Col span={4}>`, the built page uses 3 rows of 2 columns", "the chart should live in the left column of a `<Row>` split `[fill, 332px]`, currently it's stacked full-width", "the rail card is missing its `styles={{ header: { padding: 12 } }}` prop, use it to match blueprint padding". Also route missing loading states, missing Skeleton/Spin wrappers, missing empty-state UI back to this builder.
- Loop until all assertions pass. Cap: 2 cycles, then honest partial report.

## Sequencing rules

1. **Brand resolved first, once** — pick the brand and set the app theme (colours, canvas, sidebar) before any screen is built. Note the app theme only reaches chrome and colours; per-screen fidelity comes from the pre-baked blocks ([app-theme.md](../../shesha-design-system/references/app-theme.md)).
2. **Comprehend before build** — every screen has a blueprint (Step 2) before any builder is invoked. **With no design source this is Step 1b → a Tier D blueprint**, derived from the screen's archetype and the brand rather than measured. Tier D is a documented path, not a shortcut, and it still gets a blueprint: with nothing to compare against, structural drift is *harder* to notice.
3. **Route the build by walking the STRICT preference order — form-config first, custom-page last.** The blueprint header names the archetype and (for non-canonical shapes) the variant. Decision order:
   1. Is the archetype one of the five canonical CRUD shapes (`list-card` table, `list-card` datalist-of-cards, `capture` in-modal create, `record-detail`, `inline-card` row-template mini-card) AND the user's brand is compatible with the canonical Shesha look? → **`create-crud-form`** (Contract A1 — byte-exact seed copy — higher fidelity, lower turn cost than block composition).
   2. Can the screen be built with **existing** Shesha form-designer components (fields / tabs / datatables / datalists / buttonGroups / refListStatus / entityReference / etc.)? → **`shesha-form-edit`** (Contract A2).
   3. Is the ONLY gap a **missing form-designer component** — one specific capability the toolbox doesn't ship (a chart type, a rating input, an image annotator, a Kanban card, a signature pad, etc.) — and is building that component plausible? → **`create-custom-component`** (Contract A3) FIRST to widen the toolbox, THEN dispatch Contract A2 with the new component type name. **Stay on the form-configuration road.**
   4. Is the screen genuinely inexpressible even with a plausibly-new custom component (interactive drag-and-drop UIs, integration consoles with terminal semantics, marketing landing pages, bespoke data browsers with multi-selection / keyboard-shortcuts far outside form expectations)? → LAST RESORT: **`create-custom-page`** (Contract A4). Before dispatching, log in `run-log.md` the specific capability that couldn't have been a component. Do NOT reach here just because a custom page seems faster — the "speed" is you throwing away the framework's data-loader / permissions / validation / versioning / import-export.
4. **Step 4b (per-component v7+ styling) runs on `shesha-form-edit` builds only.** `create-crud-form` seeds are byte-exact and encode a specific Shesha aesthetic — grey `#fafafa` pageShell, white cards with the canonical soft shadow, radius-4 corners, blue accents, avatar circles, pill `refListStatus` cells. **That aesthetic IS the design**, documented in the seed screenshots and pinned by validator rules R14/R15. On this route the pipeline SKIPS Step 4b entirely. `create-custom-page` outputs also SKIP Step 4b — v7 blocks target Shesha form-designer components, not the AntD-native components a custom React page uses; the app theme from Step 3 supplies the colours. `shesha-form-edit` outputs go through Step 4b — its blocks arrive style-ready for the v7 overlay.
5. **Gate order** varies by builder:
   - **`shesha-form-edit`**: 5a → 5a.5 → 5b → 5c.
   - **`create-custom-page`**: 5a → 5a.5 → 5b → 5c. Same gate set — a bespoke React screen can still look generic; the critic's fixes route to `shesha-design-system` (app-theme adjustments) or back to `create-custom-page` (component polish, loading/empty states).
   - **`create-crud-form`**: 5a → 5a.5 and stop. 5b and 5c are non-runs — there's no custom theme to audit against, the critic would trivially flag the canonical Shesha look as `generic`, and applying its fixes would corrupt the seed's byte-exact aesthetic.
   A screen failing placement (5a.5) is routed back to the builder that made it, never styled over. **On `shesha-form-edit` and `create-custom-page` builds, 5c (`design-critic`) is part of the contract** — on a brief that asked for a designed result, `generic` is not done; apply its ranked fixes and re-run, or report the verdict verbatim. Cap: 2 cycles each on 5a.5 and 5c, then an honest partial report.
   On Tier D, say what 5a.5 proved: the build matches the *archetype's* intended structure, not a user's design — there wasn't one.
6. **One write path per builder** — the builder that authored the artifact owns its push. For `create-crud-form` / `shesha-form-edit` that's a form-JSON `UpdateMarkup` push; for `create-custom-component` that's package-source writes under `packages/<pkg>/src/designer-components/` (+ optional `components/`); for `create-custom-page` that's application-source writes under `src/screens/` and `src/app/`. On `shesha-form-edit` builds `shesha-design-system` returns styled paths that re-enter through `shesha-form-edit`; it does not push. On `create-crud-form` / `create-custom-page` builds `shesha-design-system` is not invoked for Step 4b at all — only for Step 3 (app theme, once per run). `clean-form-config` hands back cleaned JSON and does not push either.
7. **Multi-screen** — each screen's builder is chosen independently by walking the preference order; a run can dispatch `create-crud-form` for the CRUD screens (ship as-authored, no styling pass), `shesha-form-edit` for the settings-tab hub (form-designer components suffice), `create-custom-component` + `shesha-form-edit` for the analytics dashboard (new "bar chart" designer component, then a form-config that uses it — form-config road preserved), and `create-custom-page` only if there's genuinely a marketing landing page that couldn't have been a form. Comprehension verifies each screen's placement independently. **After every dispatch, verify the artifact on disk before accepting the agent's verdict** (see Contracts A1 / A2 / A3 / A4).
